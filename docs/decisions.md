## ADR-001: WPF вместо WinForms

**Статус:** Принято
**Контекст:** Нужен rich-text редактор с форматированием, выбором шрифтов, вставкой
изображений и переключением тем.
**Решение:** Используем WPF + MVVM.
**Альтернативы:**
- WinForms — `RichTextBox` слабее по форматированию, темы вручную, работа с изображениями
  тяжелее; FlowDocument и ResourceDictionary отсутствуют как штатные механизмы.
**Последствия:**
- Требует знания XAML/MVVM.
- Даёт `FlowDocument`/`RichTextBox` с нативным форматированием, `ResourceDictionary` для
  тем, `TextRange` для сериализации, поддержку изображений через `InlineUIContainer`.

## ADR-002: SQLite + EF Core для хранения данных

**Статус:** Принято
**Контекст:** Нужна БД для документов, настроек, версий. Команда из 6 человек, часть —
начинающие. MS SQL Server потребовал бы установки сервера у каждого.
**Решение:** SQLite как файловая БД + EF Core 8 с миграциями.
**Альтернативы:**
- MS SQL Server — лишняя инфраструктура для учебного проекта, сложнее в CI и на защите.
- Dapper — больше ручного кода, EF Core даёт миграции и change tracking «из коробки».
**Последствия:**
- БД — один файл `app.db`, ноль настройки для команды.
- Ограничения SQLite (типы, конкурентность) для нашего масштаба не критичны.
- Миграции: `dotnet ef migrations add <Name>` из проекта `TextEditor.Data`.

## ADR-003: XamlPackage как внутренний формат хранения документа

**Статус:** Принято
**Контекст:** Документ содержит форматирование и изображения. Нужен формат для хранения
в BLOB-поле БД.
**Решение:** Внутреннее хранение — `DataFormats.XamlPackage` (сериализация
`FlowDocument` через `TextRange.Save`).
**Альтернативы:**
- Сырой RTF — изображения кодируются через `\pict`, но конвертация `FlowDocument ↔ RTF`
  менее предсказуема; не все возможности форматирования переносятся 1:1.
- Собственный JSON-формат — изобретение велосипеда.
**Последствия:**
- `XamlPackage` — родной формат WPF, надёжно сохраняет текст, форматирование и изображения.
- При экспорте наружу конвертируем в `.rtf`/`.txt` через `TextRange.Save`.
- `Format` в БД означает **желаемый формат экспорта**, а не формат хранения
  (см. ADR-006).

## ADR-004: Разделение DocumentRegistry и DocumentContents

**Статус:** Принято
**Контекст:** Исходная идея — одна таблица `Documents` с BLOB-содержимым. Список
документов (Recent, поиск) тянул бы мегабайты из БД.
**Решение:** Разделить на две таблицы:
- `DocumentRegistry` — метаданные (Id, UserId, Title, Format, даты, IsFavorite).
- `DocumentContents` — BLOB содержимого (1:1 с реестром).
**Альтернативы:**
- Одна таблица — проще, но плохо масштабируется и грузит память при отображении списков.
- Отдельная таблица-связка «пользователь-документ» — избыточна, `UserId` в реестре достаточно.
**Последствия:**
- Список документов грузится без BLOB (быстро).
- Содержимое грузится только при открытии.
- Лимит 1 МБ контролируется через `CHECK (ByteSize <= 1048576)` и дублируется в сервисе.

## ADR-005: Версионирование через DocumentVersions (последние 5)

**Статус:** Принято
**Контекст:** Нужно хранить историю изменений документа «как на серверах, последние
5 версий».
**Решение:** Отдельная таблица `DocumentVersions` со снимком содержимого; логика
«оставить последние N» — в сервисе.
**Альтернативы:**
- Diff/patch-хранилище — сложнее в реализации, избыточно для MVP.
- Хранить версии внутри `DocumentContents` — нарушает нормализацию.
**Последствия:**
- Чистое версионирование; легко расширить до просмотра diff или отката.
- Удаление старых версий — при сохранении (`TrimVersionsAsync(id, keep: 5)`).
- Дополнительный объём на диске — приемлемо (5 × 1 МБ = 5 МБ на документ).

## ADR-006: Поле Format = желаемый формат экспорта, не формат хранения

**Статус:** Принято
**Контекст:** В ТЗ указано «расширения txt и rtf» для документов. При этом внутреннее
хранение — XamlPackage (ADR-003). Нужно однозначно определить смысл поля `Format`.
**Решение:** `DocumentRegistry.Format` хранит **предпочитаемый пользователем формат
экспорта** (`txt` / `rtf`). Внутреннее хранение всегда `XamlPackage`.
**Последствия:**
- При открытии документа формат экспорта известен заранее.
- При сохранении «Save» без экспорта формат игнорируется (внутри всё XamlPackage).
- При `Save As` пользователь может выбрать другой формат (с ограничениями из ADR-007).

## ADR-007: Запрет `.txt` при наличии изображений в документе

**Статус:** Принято
**Контекст:** `.txt` — plain text, не поддерживает изображения. При этом редактор
разрешает вставлять изображения в любой момент.
**Решение:** При сохранении проверяем `FlowDocument` на наличие `Image` в
`InlineUIContainer`. Если изображения есть — формат `.txt` недоступен в диалоге
сохранения (и дополнительно отсекается в валидации).
**Альтернативы:**
- Запретить вставку изображений в `.txt`-документы — плохой UX, пользователь не поймёт,
  почему вставка не работает.
- Молча терять изображения при сохранении — недопустимо.
**Последствия:**
- Диалог сохранения динамически формирует список форматов.
- Основная проверка — обход `FlowDocument` (надёжно).
- Дополнительная страховка — проверка RTF на маркер `\pict` (быстро).
- Пользователю показываем понятное сообщение, если выбрал `.txt` с изображениями.

## ADR-008: Generic Host для DI в WPF

**Статус:** Принято
**Контекст:** WPF по умолчанию не имеет DI-контейнера и стартует через `StartupUri`.
Команде нужен единый способ регистрации сервисов и конфигурации.
**Решение:** Используем `Microsoft.Extensions.Hosting` (Generic Host). `StartupUri`
убираем, `MainWindow` резолвится через `GetRequiredService`.
**Альтернативы:**
- Ручной DI через статический `ServiceLocator` — антипаттерн, плохо тестируется.
- `Microsoft.Extensions.DependencyInjection` без Host — работает, но Host даёт
  конфигурацию, логирование и управление жизненным циклом «из коробки».
**Последствия:**
- Единая точка композиции — `App.xaml.cs`.
- Миграции БД выполняются при старте (для MVP; позже можно вынести).
- Все сервисы регистрируются по интерфейсам из `Core`.

## ADR-009: CommunityToolkit.Mvvm для MVVM

**Статус:** Принято
**Контекст:** Нужна база для ViewModel без boilerplate (`INotifyPropertyChanged`,
`RelayCommand`).
**Решение:** `CommunityToolkit.Mvvm` с source generators (`[ObservableProperty]`,
`[RelayCommand]`).
**Альтернативы:**
- Реализовать `INotifyPropertyChanged` вручную — много boilerplate, риск ошибок.
- Prism / Caliburn.Micro — избыточны для нашего масштаба.
**Последствия:**
- Меньше кода, меньше ошибок.
- Source generators требуют `partial` классов — договорённость для всей команды.
- `ViewModelBase` наследует `ObservableObject` из тулкита.
